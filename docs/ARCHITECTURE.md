# معماری فنی مدرسه‌یار شهیدی

وضعیت: سند طراحی اولیه فاز صفر  
نسخه: 0.1  
تاریخ: 2026-11-15

## 1. هدف و دامنه

مدرسه‌یار شهیدی یک سامانه مدیریت آموزشی برای پایه‌های هفتم تا نهم است. سامانه باید امکان استفاده هم‌زمان دبیران و دانش‌آموزان، نگهداری مرکزی سوابق و دسترسی کنترل‌شده از موبایل و رایانه را فراهم کند.

این سند طرح هدف را مشخص می‌کند؛ وجود قابلیت‌های ذکرشده به معنی پیاده‌سازی آن‌ها در نسخه فعلی نیست.

## 2. وضعیت موجود

- وب‌سایت فعلی یک فایل استاتیک `index.html` است که از GitHub Pages منتشر می‌شود.
- داده‌ها با کلید `schoolData` در `localStorage` مرورگر نگهداری می‌شوند.
- احراز هویت، سرور برنامه، پایگاه داده مرکزی و همگام‌سازی چنددستگاهی وجود ندارد.
- فایل JSON امکان خروجی و بازیابی دستی می‌دهد؛ این سازوکار جایگزین پشتیبان‌گیری سروری نیست.

بنابراین نسخه فعلی باید به‌عنوان نمونه اولیه و مسیر موقت استفاده شود، نه سامانه عملیاتی برای داده‌های واقعی و حساس دانش‌آموزان.

## 3. تصمیم معماری پیشنهادی

### معماری کلان

1. رابط وب واکنش‌گرا و راست‌به‌چپ (RTL)
2. API امن برای همه عملیات داده‌ای
3. برنامه سمت سرور با Laravel
4. پایگاه داده PostgreSQL
5. فضای ذخیره‌سازی خصوصی برای فایل‌ها و پشتیبان‌ها
6. میزبانی ابری با TLS، پایش و ثبت رویدادها

### سبک معماری

**Modular Monolith** یا یکپارچه ماژولار انتخاب می‌شود. ماژول‌های دامنه مرزبندی روشن دارند، اما در شروع در یک برنامه Laravel مستقر می‌شوند. این انتخاب نسبت به ریزخدمت‌ها پیچیدگی عملیاتی کمتری دارد و برای اندازه فعلی پروژه کافی است.

### تصمیم‌های کلیدی

| موضوع | تصمیم اولیه | دلیل |
|---|---|---|
| Backend | Laravel | ساختار بالغ برای احراز هویت، اعتبارسنجی و منطق کسب‌وکار |
| Database | PostgreSQL | تراکنش، قیود رابطه‌ای و گزارش‌گیری قابل اتکا |
| API | REST با پیشوند `/api/v1` | ساده و قابل آزمون |
| Frontend | حفظ تدریجی رابط فعلی؛ سپس جداسازی لایه نمایش از داده | کاهش ریسک مهاجرت |
| Hosting | بک‌اند و DB روی زیرساخت ابری | دسترسی چنددستگاهی |
| Deployment | محیط آزمایشی و عملیاتی مجزا | جلوگیری از آزمایش روی داده واقعی |

GitHub Pages فقط می‌تواند میزبان فایل‌های استاتیک باشد و محل اجرای Laravel یا PostgreSQL نیست. در مرحله استقرار، رابط کاربری و API باید روی میزبان‌های مناسب خود مستقر شوند؛ دامنه و HTTPS نیز پیکربندی می‌شود.

## 4. ماژول‌های دامنه

- هویت و دسترسی: حساب‌ها، نقش‌ها، نشست‌ها و بازیابی رمز
- ساختار آموزشی: سال تحصیلی، پایه، کلاس و درس
- پرونده دانش‌آموز: مشخصات ضروری و وضعیت ثبت‌نام
- تخصیص آموزشی: دبیر، کلاس و درس
- حضور و غیاب: جلسه، وضعیت هر دانش‌آموز و ثبت‌کننده
- ارزشیابی: آزمون/تکلیف، نمره و بازخورد
- امتیازها: دفتر ثبت تراکنش امتیاز، نه فقط یک عدد قابل بازنویسی
- اطلاعیه و تکلیف: انتشار هدفمند و مشاهده
- گزارش‌ها: گزارش فردی، کلاسی و دوره‌ای
- ممیزی: ثبت عملیات حساس و تغییرات کلیدی

## 5. مدل داده اولیه

این فهرست طرح مفهومی است و پس از تأیید نیازمندی‌ها به migrationهای واقعی تبدیل می‌شود.

| موجودیت | کاربرد و ارتباط اصلی |
|---|---|
| users | اطلاعات ورود و وضعیت حساب |
| roles / user_roles | نقش مدیر، دبیر و دانش‌آموز |
| students | پرونده آموزشی؛ در صورت نیاز به حساب، پیوند کنترل‌شده با user |
| teachers | پرونده دبیر و پیوند با user |
| academic_years | سال‌های تحصیلی |
| grades / classrooms | پایه و کلاس |
| subjects | درس‌ها |
| enrollments | عضویت دانش‌آموز در کلاس در یک سال تحصیلی |
| teaching_assignments | تخصیص دبیر به کلاس و درس |
| attendance_sessions | جلسه حضور و غیاب با تاریخ و کلاس |
| attendance_records | وضعیت هر دانش‌آموز در هر جلسه |
| assessments | آزمون، تکلیف یا ارزشیابی |
| assessment_results | نمره و بازخورد دانش‌آموز |
| assignments / submissions | تکلیف و تحویل آن |
| point_transactions | افزایش/کاهش امتیاز با دلیل و ثبت‌کننده |
| announcements | اطلاعیه و مخاطبان |
| audit_logs | ثبت تغییرات حساس |

### قواعد یکپارچگی داده

- هر دانش‌آموز در یک سال تحصیلی باید ثبت‌نام‌های مشخص و بدون تکرار داشته باشد.
- برای هر جلسه حضور و غیاب، حداکثر یک رکورد برای هر دانش‌آموز مجاز باشد.
- نمره، حضور و غیاب و امتیاز باید به سال تحصیلی، کلاس و ثبت‌کننده قابل ردیابی باشند.
- حذف پرونده دارای سابقه آموزشی نباید موجب حذف آبشاری سوابق شود؛ از بایگانی/غیرفعال‌سازی و سیاست نگهداری استفاده شود.
- تاریخ‌ها در پایگاه داده به‌صورت استاندارد ذخیره و در رابط کاربری با تقویم و قالب فارسی نمایش داده شوند.
- تغییرات مهم باید زمان، کاربر و موضوع تغییر را ثبت کنند.

## 6. نقش‌ها و مجوزها

### مدیر سامانه/مدرسه
مدیریت کاربران، سال تحصیلی، کلاس‌ها، تخصیص‌ها و گزارش‌های مجاز.

### دبیر
دسترسی فقط به کلاس‌ها و درس‌های تخصیص‌یافته؛ ثبت حضور و غیاب، ارزشیابی و تکالیف در محدوده مجاز.

### دانش‌آموز
مشاهده فقط پرونده، نمرات، حضور و غیاب، تکالیف و اطلاعیه‌های متعلق به خودش. دانش‌آموز نباید امکان تغییر داده‌های رسمی را داشته باشد.

### والدین
در نسخه نخست خارج از دامنه؛ در آینده فقط با فرایند احراز و پیوند قانونی/مجاز به دانش‌آموز اضافه شود.

**اصل امنیتی:** پنهان‌کردن دکمه در رابط کاربری کافی نیست. مجوز هر درخواست باید در سمت سرور و روی منبع مورد دسترسی بررسی شود.

## 7. قرارداد API اولیه

نمونه مسیرهای پیشنهادی؛ هنوز پیاده‌سازی نشده‌اند:

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/me`
- `GET /api/v1/classes`
- `GET /api/v1/classes/{class}/students`
- `POST /api/v1/classes/{class}/attendance-sessions`
- `PUT /api/v1/attendance-sessions/{session}/records`
- `GET /api/v1/students/{student}/report`
- `GET /api/v1/assessments`

تمام ورودی‌ها باید اعتبارسنجی شوند؛ خطاها پاسخ ساخت‌یافته داشته باشند؛ عملیات حساس ثبت ممیزی شوند. API نباید داده‌های یک دانش‌آموز را به کاربر دیگر افشا کند.

## 8. امنیت، حریم خصوصی و پایداری

- HTTPS اجباری؛ هیچ رمز یا کلید محرمانه‌ای در مخزن Git ثبت نشود.
- رمز عبور با الگوریتم امن و مدیریت‌شده توسط چارچوب ذخیره شود؛ رمز خام ممنوع.
- محدودسازی تلاش ورود، نشست امن، محافظت CSRF در صورت استفاده از نشست/کوکی و اعتبارسنجی سمت سرور.
- دسترسی DB از اینترنت عمومی مسدود و فقط از سرویس برنامه مجاز باشد.
- اصل حداقل دسترسی برای مدیر، دبیر و دانش‌آموز.
- ثبت ممیزی بدون درج رمز، توکن یا اطلاعات غیرضروری حساس.
- پشتیبان رمزگذاری‌شده و خارج از ماشین اصلی؛ سیاست نگهداری و آزمون بازیابی پیش از بهره‌برداری تعریف شود.
- داده آزمایشی ساختگی باشد؛ داده واقعی فقط پس از تأیید امنیت، مجوزها، سیاست حریم خصوصی و محل میزبانی وارد شود.
- پیش از انتخاب ارائه‌دهنده ابری، کشور محل نگهداری داده، شرایط پردازش داده و الزامات قانونی قابل‌اعمال بررسی شود.

## 9. مهاجرت از نسخه فعلی

1. حفظ نسخه فعلی و تهیه نسخه پشتیبان از کد.
2. طراحی مدل داده و قواعد اعتبارسنجی.
3. پیاده‌سازی API و آزمون آن با داده ساختگی.
4. ساخت لایه ارتباط رابط وب با API؛ تا آن زمان نسخه فعلی فقط نمونه اولیه باقی می‌ماند.
5. نوشتن مبدل یک‌باره برای فایل JSON قدیمی، با گزارش تعداد رکوردهای پذیرفته/ردشده.
6. اجرای مهاجرت آزمایشی و تطبیق تعداد دانش‌آموزان، حضورها و امتیازها.
7. مهاجرت واقعی فقط با تأیید مسئول مجاز، نسخه پشتیبان و امکان بازگشت.

هرگز نباید داده‌های localStorage مرورگر به‌طور خودکار یا بدون کنترل به پایگاه داده عملیاتی ارسال شوند.

## 10. معیار آمادگی برای بهره‌برداری

- آزمون‌های خودکار مجوزها برای هر نقش
- آزمون جلوگیری از دسترسی دانش‌آموز به داده دیگری
- آزمون یکپارچگی حضور و غیاب و نمرات
- آزمون بازیابی پشتیبان در محیط جداگانه
- بررسی امنیتی پیکربندی و وابستگی‌ها
- آزمون موبایل و راست‌به‌چپ
- تأیید فرایند پشتیبانی، مدیریت خطا و گزارش رخداد

## 11. مواردی که هنوز باید تصمیم‌گیری شوند

- تعداد تقریبی دبیران و دانش‌آموزان و تعداد مدارس (در نسخه اول یک مدرسه فرض شده است).
- آیا دانش‌آموزان حساب مستقل خواهند داشت یا فقط دبیران در نسخه اول وارد می‌شوند؟
- روش شناسه ورود: نام کاربری، شماره دانش‌آموزی یا روش دیگر.
- تقویم و منطقه زمانی مورد استفاده.
- محل مجاز نگهداری داده و ارائه‌دهنده ابری.
- الزامات رسمی مدرسه برای نمره، کارنامه، نگهداری و دسترسی به داده‌ها.
