# طراحی احراز هویت و مجوزهای مدرسه‌یار شهیدی

**وضعیت:** طرح پیشنهادی؛ هنوز پیاده‌سازی نشده  
**تاریخ:** ۱۵ نوامبر ۲۰۲۶

## ۱. نقش‌های نسخه اول

| نقش | دامنه دسترسی |
|---|---|
| `school_admin` | مدیریت کاربران، سال تحصیلی، کلاس‌ها، درس‌ها، تخصیص‌ها و گزارش‌های مجاز مدرسه |
| `teacher` | فقط کلاس‌ها و درس‌های تخصیص‌یافته؛ ثبت حضور و غیاب، ارزشیابی و تکلیف در همان محدوده |
| `student` | فقط پرونده، کلاس، نمرات، حضور و غیاب، تکالیف و اطلاعیه‌های متعلق به خودش |

والدین در نسخه اول خارج از دامنه هستند. نقش‌ها در سمت سرور ارزیابی می‌شوند؛ مخفی‌کردن کنترل‌های رابط کاربری جایگزین مجوز سرور نیست.

## ۲. حساب‌ها و شناسه ورود

- جدول مشترک `users` برای احراز هویت؛ نام کاربری یکتا، رمز عبور هش‌شده و وضعیت فعال/غیرفعال.
- ثبت‌نام عمومی غیرفعال است؛ حساب‌ها فقط توسط مدیر مجاز مدرسه ساخته یا فعال می‌شوند.
- نام کاربری دبیر توسط مدرسه تعیین می‌شود.
- نام کاربری پیشنهادی دانش‌آموز، کد داخلی دانش‌آموز است؛ کد ملی یا شماره تلفن به‌عنوان شناسه ورود پیش‌فرض استفاده نمی‌شود.
- حساب دانش‌آموز به یک پرونده `students` و حساب دبیر به یک پرونده `teachers` پیوند یکتا خواهد داشت.
- غیرفعال‌کردن حساب باید دسترسی را فوراً قطع و توکن‌های فعال را باطل کند.
- بازیابی رمز باید فرایند کنترل‌شده مدرسه داشته باشد؛ رمز اولیه موقت بوده و در اولین ورود تغییر داده شود.

## ۳. فناوری احراز هویت

Laravel Sanctum گزینه پیشنهادی برای پشتیبانی از نشست SPA و توکن API است. انتخاب نهایی روش اتصال مرورگر به API به دامنه استقرار بستگی دارد:

- اگر رابط وب و API روی یک دامنه اصلی یا زیردامنه‌های همان دامنه باشند، احراز هویت نشست/کوکی Sanctum با CSRF ترجیح دارد.
- اگر رابط روی GitHub Pages با دامنه `github.io` بماند و API روی دامنه‌ای مستقل میزبانی شود، این دو مبدأ برای کوکی first-party هم‌دامنه نیستند. پیش از انتشار باید دامنه سفارشی و معماری CORS/کوکی تعیین شود.
- برای کلاینت‌های موبایل یا مصرف‌کننده‌های API مستقل، توکن‌های شخصی Sanctum قابل استفاده‌اند؛ توکن خام فقط یک‌بار به کاربر نمایش داده شود، هش آن در پایگاه داده ذخیره شود و امکان لغو وجود داشته باشد.
- توکن Bearer نباید بدون تصمیم امنیتی روشن در `localStorage` مرورگر ذخیره شود. Sanctum token abilities نیز جایگزین Policy و بررسی مالکیت رکورد نیست.

## ۴. مجوزدهی

- استفاده از Policy برای هر منبع: دانش‌آموز، کلاس، جلسه حضور و غیاب، ارزشیابی و گزارش.
- مدیر مدرسه فقط در محدوده همان مدرسه مجاز است.
- دبیر باید علاوه بر نقش، تخصیص فعال به کلاس/درس موردنظر داشته باشد.
- دانش‌آموز باید به‌واسطه پیوند حساب با پرونده خودش به داده دسترسی یابد؛ شناسه ارسالی از سمت مرورگر به‌تنهایی قابل اعتماد نیست.
- همه endpointهای خصوصی به‌صورت پیش‌فرض نیازمند احراز هویت هستند؛ فقط health endpoint عمومی می‌ماند.
- آزمون‌های منفی باید دسترسی ناشناس، دسترسی دبیر به کلاس غیرتخصیص‌یافته و دسترسی دانش‌آموز به پرونده دیگران را رد کنند.

## ۵. کنترل‌های امنیتی پایه

- هش رمز با قابلیت Hash چارچوب؛ عدم ذخیره یا ثبت رمز خام.
- محدودسازی نرخ ورود و پاسخ خطای عمومی برای نام کاربری/رمز اشتباه.
- ثبت زمان آخرین ورود و رویدادهای امنیتی بدون ذخیره رمز، توکن یا داده حساس.
- ابطال نشست/توکن هنگام غیرفعال‌سازی حساب یا تغییر رمز.
- اصل حداقل دسترسی برای پایگاه داده و سرویس برنامه.
- استفاده از HTTPS در محیط عملیاتی؛ TLS فقط در سرویس محلی تست می‌تواند غیرفعال باشد.
- ورود اطلاعات واقعی فقط پس از تکمیل Policyها، آزمون امنیتی و تعیین محل میزبانی مجاز است.

## ۶. موارد باز پیش از پیاده‌سازی

1. آیا دانش‌آموزان از روز اول حساب مستقل می‌خواهند یا ابتدا فقط دبیران و مدیر وارد می‌شوند؟
2. آیا رابط و API روی دامنه سفارشی مشترک مستقر خواهند شد؟
3. روش تحویل رمز اولیه و بازیابی رمز در مدرسه چیست؟
4. چه کسی نقش مدیر مدرسه را دارد و فرایند جایگزینی مدیر چگونه کنترل می‌شود؟

تا زمان پاسخ به این موارد، هیچ حساب واقعی، رمز واقعی یا endpoint ورود عمومی ساخته نمی‌شود.
